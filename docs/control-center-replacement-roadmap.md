# Control Center Replacement Roadmap — 18 Phases (Phase 0 deliverable)

Documented only. Implementation does not begin from this document — per the brief, Phase 1 requires separate authorization. Each phase lists objective, dependencies, what's reused vs. replaced, and impact/migration/testing/risk. Phases lean on the preservation plan and public-site integration plan above rather than repeating their detail.

## Phase 1 — Control Center Shell
**Objective**: Add a "Website" top-level nav section (11 sections today → 12), no functional change yet.
**Dependencies**: none. **Reuse**: `NAV_ITEMS`/`Sidebar.tsx`/`AppShell.tsx` pattern, unchanged. **Replace**: nothing. **DB impact**: none. **API impact**: none. **Frontend impact**: one new nav section, placeholder pages. **Public-site impact**: none. **Migration**: none. **Testing**: nav visibility/permission-gating test only. **Risks**: none — purely additive scaffolding.

## Phase 2 — Site Editor
**Objective**: A composition UI for assembling a page from template parts/sections (design surface, not final content authoring).
**Dependencies**: Phase 4 (Templates/Template Parts) should land first in practice — listed here per the brief's fixed numbering, but implementation order should follow the dependency, not the number.
**Reuse**: existing `RichTextEditor`(TipTap) for text regions. **Replace**: nothing existing. **DB impact**: none new beyond Phase 4's. **API impact**: composition state persisted via Phase 4's Template/TemplatePart endpoints. **Frontend impact**: new, substantial (drag/compose UI). **Public-site impact**: none until Phase 5. **Migration**: none. **Testing**: new integration + component tests. **Risks**: largest net-new frontend surface in the whole roadmap — scope tightly (start with section reordering, not free-form drag-drop) to avoid an open-ended build.

## Phase 3 — Site Identity + Global Styles
**Objective**: Org-scoped name/logo/tagline/contact + color/font tokens, editable in the CC.
**Dependencies**: none. **Reuse**: `SystemSetting` (extend with `site.*`/`theme.*` keys — see data-preservation plan; no new table unless token count proves it out). **Replace**: nothing. **DB impact**: none (or one new `GlobalStyle` table only if Global Styles' field count outgrows key/value — decide at implementation time). **API impact**: `GET/PATCH /settings` already exists; add typed convenience endpoints only if the flat KV proves awkward for the frontend. **Frontend impact**: new Settings sub-pages. **Public-site impact**: `artifysolscom` build/runtime must read these values instead of hardcoded constants — first real coupling change. **Migration**: seed default values matching today's hardcoded artifysolscom branding so nothing visually changes at cutover. **Testing**: value round-trip + artifysolscom render-with-new-values smoke test. **Risks**: cutover must be seeded correctly or the live site's branding regresses instantly — treat the seed step as the risk-bearing step, not the schema.

## Phase 4 — Templates + Template Parts
**Objective**: `Template`/`TemplatePart` models (per data-preservation plan), `Page.templateId` FK.
**Dependencies**: none. **Reuse**: `Page` model (additive column only). **Replace**: nothing. **DB impact**: 2 new tables + 1 additive nullable column on `Page`, zero-downtime. **API impact**: new `templateRoutes.ts`/`templatePartRoutes.ts`, new `templates.*`/`template_parts.*` permission keys. **Frontend impact**: new CC pages to manage templates/parts. **Public-site impact**: none yet — `artifysolscom` doesn't consume templates until Phase 5+. **Migration**: existing pages default `templateId = null` → render via today's existing per-page-type component (no regression). **Testing**: full CRUD + permission integration tests, matching the `findByIdInOrg` convention. **Risks**: template/region JSON shape needs to survive Phases 5–6's real usage without a redesign — prototype against one real page type before generalizing.

## Phase 5 — Navigation + Pages + Homepage
**Objective**: `NavigationMenu`/`MenuItem` models; `artifysolscom` header/footer/homepage-anchors start reading from them; homepage becomes a `Page` (via `SystemSetting` "homepageId" or `Page.isHomepage`) rendered through Phase 4's templates.
**Dependencies**: Phase 3 (Site Identity, for consistent branding in nav), Phase 4 (Templates). **Reuse**: `Page`, `Redirect` (for menu-link 404 fallback per the public-site integration plan). **Replace**: `artifysolscom`'s hardcoded nav arrays and the 16-hardcoded-section homepage tree — **the single largest replacement in the roadmap**; sequence it last within this phase, after menus prove out on non-homepage nav. **DB impact**: 2 new tables. **API impact**: new `menuRoutes.ts`, public `GET /public/menus/:key`. **Frontend impact**: CC menu-builder UI; `artifysolscom` router/header/footer refactor. **Public-site impact**: highest of any phase — real production nav/homepage swap. **Migration**: seed menus from today's hardcoded link sets exactly, verify parity before cutover. **Testing**: `artifysolscom` route/nav integration tests (existing `tests/` suite already covers Blog/CmsPageRoute patterns to extend), visual smoke test pre/post cutover. **Risks**: highest production-visible risk in the roadmap — stage behind a flag or a preview deployment before flipping the live homepage; a bad seed silently breaks primary navigation on the production marketing site.

## Phase 6 — Patterns + Components + Media
**Objective**: Reusable section "patterns" (pre-built template-part combinations) library; media-library UX upgrade for Website use.
**Dependencies**: Phase 2, Phase 4. **Reuse**: `MediaAsset` as-is. **Replace**: nothing. **DB impact**: possibly one `Pattern` table (a named, reusable `TemplatePart` combination) — evaluate necessity once Phase 4/5 usage patterns are real. **API impact**: new pattern endpoints if the table is built. **Frontend impact**: pattern picker in Site Editor. **Public-site impact**: none directly (patterns are an authoring convenience). **Migration**: none. **Testing**: CRUD tests if new table added. **Risks**: low — the deferrable, nice-to-have phase in this cluster; can slip without blocking Phases 7+.

## Phase 7 — Professional Content Management
**Objective**: Close the remaining Content gaps: real SEO-field UI depth beyond the current form fields, editorial workflow (draft/review states) if not already sufficient.
**Dependencies**: none new. **Reuse**: `Post`/`Page`/`ContentRevision` entirely as-is. **Replace**: nothing. **DB impact**: none expected. **API impact**: none expected — existing content routes suffice. **Frontend impact**: UI depth only. **Public-site impact**: none. **Migration**: none. **Testing**: existing coverage extends. **Risks**: low — this phase should mostly be found to already be "close enough" per the gap analysis (Content is EXISTING/WORKING); verify scope is real before spending a full phase here.

## Phase 8 — Advanced SEO
**Objective**: Fix the crawler-visibility gap (task #64) — SSR/prerender/edge-injection for meta/OG/JSON-LD; build the expanded SEO panel (task #66).
**Dependencies**: none new, but this is the highest-value phase for the public site's actual SEO performance — consider pulling it earlier than #8 in implementation order.
**Reuse**: existing `seo.ts`/`sitemap.ts`/`Redirect` model entirely. **Replace**: the client-side-only meta-injection *mechanism* (not the data it injects). **DB impact**: none, or one `SeoAnalysisResult` table if #66's content-analysis needs persisted results. **API impact**: possibly a new edge/SSR entry point in `api/index.ts` (artifysolscom's existing serverless function) rather than a Platform API change. **Frontend impact**: CC SEO panel UI. **Public-site impact**: real, positive — actual indexability improvement, the fix this whole SEO domain has been missing. **Migration**: none. **Testing**: crawler-simulation test (fetch HTML without executing JS, assert meta present) — new test category, add it. **Risks**: SSR/prerender is an architectural decision (Vite SSR vs. prerender-at-build vs. edge middleware) — needs its own design pass before implementation, don't guess the mechanism inside this roadmap.

## Phase 9 — Forms + Landing Pages + Conversion
**Objective**: Public-facing dynamic form renderer on artifysolscom (Forms already exist backend-side, Phase 9 of the prior roadmap); Landing Pages (`Page.pageType`) go live; UTM capture extends to the original `ContactAndBrief` form, not just new Forms submissions.
**Dependencies**: Phase 4/5 (Templates/Pages) for Landing Page rendering. **Reuse**: `Form`/`FormSubmission`, `Page`. **Replace**: nothing (ContactAndBrief keeps working, gains UTM capture — additive). **DB impact**: `Page.pageType` enum column (additive). **API impact**: public `GET /public/forms/:slug`, `POST /public/forms/:slug/submit` already exist — wire the renderer to them. **Frontend impact**: new artifysolscom form-renderer component; CC gets Landing Page authoring. **Public-site impact**: real, new conversion surface. **Migration**: none. **Testing**: form-render + submit integration test, landing-page-render test. **Risks**: low — mostly wiring existing backend capability to a new frontend surface.

## Phase 10 — Products + Services + Solutions
**Objective**: Make `/solutions`, `/services`, `/industries` (currently 100% hardcoded) partially or fully Catalog/Landing-Page-driven.
**Dependencies**: Phase 9 (Landing Pages) for any page-level conversion. **Reuse**: `Product`/`ProductModule` (already API-driven for `/ai-solutions`) as the pattern to extend to the remaining hardcoded catalog-adjacent pages. **Replace**: hardcoded `ServicesPage.tsx`/`IndustriesPage.tsx`/`SolutionsCatalogPage.tsx` content, incrementally. **DB impact**: none expected beyond what Catalog already has, unless Services/Industries prove to need their own entities (evaluate at implementation time, don't pre-build). **API impact**: possibly new `GET /public/services`, `/public/industries` if those become real content types rather than static pages. **Frontend impact**: real. **Public-site impact**: real, positive (removes 3 of the largest remaining hardcoded pages). **Migration**: content migration — hardcoded copy needs to become authored data before cutover. **Testing**: existing `AiSolutionsPage.test.tsx` pattern extends. **Risks**: content-migration effort (someone must author what's currently hardcoded) is larger than the engineering effort — flag as a content/product-ops dependency, not purely technical.

## Phase 11 — Case Studies + Content Relationships
**Objective**: Formalize Case Studies (already real CMS Posts under a category — confirmed this audit, not static) with proper relationships to Products/Industries if that linkage is needed; resolve the fake-case-studies content-honesty concern from the prior (09-26) audit if it still applies.
**Dependencies**: none new. **Reuse**: `Post`+`Category` (already working). **Replace**: nothing structural — verify first whether the "fabricated case studies" finding from the older audit still holds (re-check case-study *content*, not the mechanism, which is confirmed real). **DB impact**: none expected, or a lightweight `Post`↔`Product` relation table if cross-linking is a real requirement. **API impact**: none expected. **Frontend impact**: minor. **Public-site impact**: minor. **Migration**: none. **Testing**: existing. **Risks**: low — mostly a content-accuracy verification task, not an engineering build.

## Phase 12 — CRM Integration
**Objective**: Wire Website/Marketing conversion events (form submissions, landing-page CTAs) more richly into CRM (already converts to Lead) — e.g. landing-page-level attribution on the Lead record.
**Dependencies**: Phase 9. **Reuse**: `Lead`, `Opportunity` entirely. **Replace**: nothing. **DB impact**: possibly `Lead.landingPageId` (additive, nullable). **API impact**: extend existing lead-creation path, not a new one. **Frontend impact**: CRM dashboard gains landing-page-source visibility. **Public-site impact**: none directly. **Migration**: none. **Testing**: extend existing CRM integration tests. **Risks**: low.

## Phase 13 — Clients + Onboarding
**Objective**: Verify Clients/Onboarding/Portal need nothing new from this initiative (they're already EXISTING/WORKING) — this phase should mostly close as "no work found," confirming rather than building.
**Dependencies**: none. **Reuse**: everything. **Replace**: nothing. **DB/API/Frontend/Public-site impact**: none expected. **Migration**: none. **Testing**: none new expected. **Risks**: none — include this phase only to formally confirm the gap analysis's finding, not to manufacture work.

## Phase 14 — Marketing + Automation
**Objective**: Campaign/attribution reporting (the piece of Marketing still MISSING per the gap analysis); optionally a minimal frontend for the already-real, backend-only Automation engine if workflow authoring is meant to be user-facing under "Operations."
**Dependencies**: Phase 15 (Analytics) for real attribution data — campaign reporting without pageview/traffic data is limited to CRM-sourced conversion counts only; sequence accordingly even though numbered 14.
**Reuse**: `Form`/`FormSubmission`/`Lead` for conversion counts; `AutomationWorkflow` etc. entirely for Automation UI, if built. **Replace**: nothing. **DB impact**: none expected for reporting (aggregation over existing tables); none for an Automation UI (schema already complete). **API impact**: new read/aggregation endpoints only. **Frontend impact**: new dashboard(s). **Public-site impact**: none. **Migration**: none. **Testing**: new integration tests for aggregation endpoints. **Risks**: scope creep — "campaign/attribution" can expand indefinitely; cap this phase at CRM-sourced conversion counts unless Phase 15 lands first.

## Phase 15 — Analytics
**Objective**: Resolve the still-open product decision (self-built pageview pipeline vs. integrate an existing provider e.g. Plausible/GA4) — this phase cannot be scoped further until that decision is made.
**Dependencies**: a product decision, not an engineering one — this remains the single blocking non-technical item in the whole roadmap, unchanged from the prior roadmap's finding. **Reuse**: n/a until decided. **Replace**: n/a. **DB impact**: new `PageView`/`AnalyticsEvent` tables if self-built; none if integrating a provider. **API impact**: new ingestion endpoint if self-built; none if integrating. **Frontend impact**: new dashboards either way. **Public-site impact**: a tracking snippet either way (currently confirmed absent entirely) — privacy/consent implications either path, should be scoped alongside the decision. **Migration**: none. **Testing**: n/a until scoped. **Risks**: the only phase in this roadmap that cannot start on engineering judgment alone.

## Phase 16 — Workflows + Approvals + Operations
**Objective**: Regroup existing Commerce (Contract/Subscription/Invoice/Payment) + the real-but-headless Automation engine under an "Operations" IA grouping; give Automation a frontend if warranted; fix the two mocked Automation actions (`create_invoice_draft`, `generate_report`) found this audit.
**Dependencies**: none blocking — this is mostly IA regrouping + two targeted bug fixes. **Reuse**: everything (Commerce fully built; Automation engine fully built minus 2 actions). **Replace**: `ActionRegistry.ts`'s 2 mocked action handlers — wire to real `invoiceService`/a real reporting service. **DB impact**: none. **API impact**: none beyond nav regrouping. **Frontend impact**: nav-section move (Commercial → Operations, or add Operations alongside); new Automation UI if scoped. **Public-site impact**: none. **Migration**: none. **Testing**: fix and add a regression test for the two mocked actions specifically. **Risks**: low — well-bounded, mostly a correctness fix plus IA cleanup.

## Phase 17 — Security + Administration + Integrations
**Objective**: Close Administration's one real gap (custom roles, currently read-only/system-only) if warranted by then; resolve the 6 vestigial AI/Automation/Knowledge/Copilot permission keys found this audit (add the missing route, or remove the key); address Knowledge's mock-embedding-fallback risk if RAG quality becomes a real product requirement.
**Dependencies**: none blocking. **Reuse**: `RolePermission` join-table shape generalizes to org-defined roles per the data-preservation plan. **Replace**: nothing forced — evaluate whether custom roles are a confirmed need before building (same discipline the existing roadmap already applied to the deferred Company-entity gap). **DB impact**: `Role.organizationId`/`isSystemRole` (additive) only if custom roles are built. **API impact**: new role-CRUD routes only if built. **Frontend impact**: RolesPage gains edit capability only if built. **Public-site impact**: none. **Migration**: none. **Testing**: extend `tests/security/rbacAndAudit.test.ts` if roles become mutable. **Risks**: low, but don't build custom roles speculatively — confirm the need first, exactly as this initiative's own stated discipline requires.

## Phase 18 — AI Control Center + Final Production QA
**Objective**: Verify AI/Copilot/Automation/Knowledge need nothing new from this initiative beyond Phase 16/17's targeted fixes; run a full production-readiness QA pass across everything touched by Phases 1–17 (auth/RBAC untouched-by-design verification, tenant isolation re-proof, full regression suite, artifysolscom production smoke test, rollback plan review for the highest-risk phase — Phase 5's homepage/nav cutover).
**Dependencies**: all prior phases. **Reuse**: existing test suites (tests/security/*, tests/integration/*, artifysolscom's tests/*) as the QA backbone — extend, don't replace. **Replace**: nothing. **DB/API impact**: none new — this is a verification phase. **Frontend impact**: none new. **Public-site impact**: final production verification only. **Migration**: none. **Testing**: this phase IS testing — full suite run, plus the crawler-simulation test from Phase 8 and the visual-parity check from Phase 5, re-run against the final state. **Risks**: the phase most likely to surface issues from *earlier* phases rather than create new ones — budget real time for it, don't treat it as a formality.

## Sequencing note

The brief's phase numbering is fixed as delivered above; several dependency notes above (Phase 2 before 4 in practice, Phase 15 informing 14, Phase 8 pulled earlier for SEO value) flag where **implementation order should deviate from the listed numbers** — this is intentional and should be decided explicitly when Phase 1 begins, not silently reordered.
