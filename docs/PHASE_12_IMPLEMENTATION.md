# Phase 12 — AI Control Center & Governed Automation

Implementation notes, scoped to the brief: a governed AI-automation subsystem — provider/model catalog, a tool registry with strict permission/tenant/risk-tier enforcement, versioned prompt templates, bounded deterministic workflows, a human-approval gate for HIGH-risk actions, usage/cost tracking, AI-specific audit logging, AI-specific rate limiting, and a full Control Center UI. No autonomous agent loop, no background/async execution, no live payment gateway changes. See `docs/AI_ARCHITECTURE.md`, `docs/AI_GOVERNANCE.md`, `docs/AI_TOOL_SECURITY.md`, `docs/AI_WORKFLOW_ARCHITECTURE.md`, `docs/AI_USAGE_AND_COSTS.md` for the architecture and `docs/PHASE_12_COMPLETION_REPORT.md` for status.

## What changed, and why

### 1. Database migration
One migration, `prisma/migrations/20260921100313_phase12_ai_control_center/`, adding 8 enums (`AIProviderStatus`, `AIRiskLevel`, `AIToolStatus`, `AIPromptStatus`, `AIWorkflowStatus`, `AIExecutionKind`, `AIExecutionStatus`, `AIApprovalStatus`) and 11 models (`AIProvider`, `AIModel`, `AITool`, `AIOrgToolSetting`, `AIPromptTemplate`, `AIPromptVersion`, `AIWorkflow`, `AIExecution`, `AIToolExecution`, `AIUsageRecord`, `AIApprovalRequest`) plus their back-relations on `User`/`Organization`. Verified both from a clean database (all 11 migrations apply in order) and as an upgrade from the Phase 10 schema (reset-and-reapply against this sandbox's local dev database, with the user's own explicit, disclosed consent per Prisma's AI-agent safety guard before running `migrate reset`).

### 2. Permission catalog
The Phase 2 placeholder keys `ai.use`/`ai.manage` are retired in favor of 22 granular `ai.*` keys (`server/types/domain.ts`) — provider/model/tool catalog administration separate from prompt/workflow authoring, separate from execution, separate from approval decisions, separate from usage/audit reads — mirroring Phase 10 §34's split between read/write and sensitive-transition permissions. `prisma/rolePermissionSeed.ts` grants: ADMIN the full set; MANAGER catalog-read plus author/execute/read-pending-approvals but not catalog administration or approval decisions; USER execute-and-read-own but no authoring; VIEWER read-only across every AI surface including AI-specific audit. No existing key was removed without a replacement — `ai.use`/`ai.manage` had zero real usage (Phase 1 explicitly built no AI business routes yet), verified before retiring them.

### 3. Governance layer
`server/ai/toolRegistry.ts` (10 real tools, each a thin wrapper around an existing service — no parallel AI business logic) and `server/ai/governance.ts` (the single dispatcher every tool call goes through: permission check, org enablement, input validation, risk/approval gate, execution, audit). `server/ai/tools.ts`, the Phase 1 empty-registry placeholder, is deleted — fully superseded. `server/ai/provider.ts`'s `AiProvider.generateText` now returns `{text, model, usage?}` instead of a bare string, reading the Gemini SDK's own token-usage metadata when available. `prisma/aiToolSeed.ts` syncs the code registry into the `ai_tools` table on every boot/test-setup, the same pattern `rolePermissionSeed.ts` established for permissions.

### 4. Backend additions
Repositories (`aiProviderRepository`, `aiToolRepository`, `aiPromptRepository`, `aiWorkflowRepository`, `aiExecutionRepository`, `aiUsageRepository`, `aiApprovalRepository`) follow the established `findByIdInOrg`-only convention for every organization-scoped model. Services (`aiProviderService`, `aiToolService`, `aiPromptService`, `aiWorkflowService`, `aiExecutionService`, `aiUsageService`, `aiApprovalService`) follow the Phase 10 `(caller: SanitizedUser, input, meta: RequestMeta)` + `auditLogRepository.record()`-on-every-mutation pattern. `aiWorkflowService.executeWorkflow` and `aiExecutionService.executeTool` are the two entry points into `server/ai/governance.ts`; `aiApprovalService.decide` is the third (approval execution), re-resolving the original requester via a newly-exported `authService.resolveSanitizedUserForOrganization` rather than trusting the approver's own identity for the eventual action.

### 5. Endpoints
See `docs/AI_ARCHITECTURE.md` §"Endpoints" for the full table — 7 route files mounted under `/api/v1/ai/*` (`aiProviderRoutes`, `aiToolRoutes`, `aiPromptRoutes`, `aiWorkflowRoutes`, `aiExecutionRoutes`, `aiUsageRoutes`, `aiApprovalRoutes`), each `authenticateToken` + `requirePermission` + `asyncHandler` + Zod `.parse()`, matching every other Phase 3-10 route file's shape exactly.

### 6. AI-specific rate limiting
`aiExecutionLimiter` (`server/middleware/rateLimiter.ts`) — 30 requests/5 minutes, keyed per-caller — applied to the two execution-triggering endpoints (`POST /ai/workflows/:id/execute`, `POST /ai/executions/tool-call`), tighter than `generalApiLimiter` since each call can reach an external provider or mutate real data.

### 7. Frontend
`src/lib/aiApi.ts` — the typed client for all 7 AI sub-domains, following the same `paginatedGet`/`apiClient` conventions Phase 10's commercial modules established (`paginatedGet` exported from `src/lib/api.ts` for reuse). Eight Control Center pages under `src/components/modules/ai/`: `AiOverviewPage` (real data only, degrading per-permission, never fabricating a metric — same convention as `CrmDashboardPage`), `AiProvidersPage`, `AiToolsPage` (with a permission-gated per-tool enable/disable toggle), `AiPromptsPage` (create/version/publish/archive), `AiWorkflowsPage` (a dynamic step builder against the live tool catalog, publish, run), `AiExecutionsPage` (master-detail execution history with per-step tool-execution detail and JSON output view), `AiUsagePage`, `AiApprovalsPage` (approve/reject, gated by `ai.approvals.decide`). Registered in `src/lib/permissions.ts`'s `NAV_ITEMS` under a new `"AI"` section, added to `Sidebar.tsx`'s `SECTIONS` list — no new routing mechanism, reusing the existing config-driven nav/router wiring exactly.

### 8. Deliberate Phase 12 scope boundaries
No autonomous LLM tool-calling loop (`AIExecutionKind` has only `TOOL_CALL`/`WORKFLOW`, no general chat kind). No background/async execution — a workflow run is synchronous within its triggering request. No retry/resume for a failed or approval-gated workflow. No budget/spend-limit enforcement on usage. No live payment gateway involvement — `invoices.issue`/`contracts.activate` call the same Phase 10 services a human uses, unchanged. No notification when an approval is pending (Phase 13's territory). See `docs/AI_ARCHITECTURE.md` for the full boundary list.
